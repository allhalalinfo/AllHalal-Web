# Промпт для Backend: картинки статей вместо плейсхолдеров (AllHalal)

**Скопируйте всё от раздела «НАЧАЛО ПРОМПТА» до «КОНЕЦ ПРОМПТА»** и отправьте backend-разработчику или Backend AI.  
**Проект:** allhalal.info · **Клиент:** Next.js (Vercel), данные с Hetzner FastAPI.

---

## НАЧАЛО ПРОМПТА

### Роль и цель

Ты — backend-инженер FastAPI/сервиса агрегации. Нужно **устранить ситуацию, когда пользователи видят плейсхолдеры / одно и то же generic-фото** вместо превью статей.

**Цель продукта:** для большинства записей в лентах отдавать **стабильный абсолютный URL реальной картинки статьи** (как на сайте источника), чтобы веб мог её показать.

**Важно:** проблема не только «красивый UI». Если в JSON **нет** `imageUrl`/`image_url`, или URL ведёт на **403/HTML**, или **один Pexels на десятки статей**, пользователь воспринимает это как «сломались картинки».

---

### Где это используется на фронте (контракт)

1. **Новости (News)**  
   Клиент запрашивает: `GET /api/v1/news/cached` (query: `safe_only`, `limit`, опционально `category`).  
   В каждом элементе массива `items` ожидается поле **`imageUrl`** (camelCase) **или** то же семантически как `image_url` — **согласуй с текущим ответом API и с тем, что реально парсит фронт**; в репозитории фронта тип: `imageUrl: string | null` (`lib/newsFeed.ts`).

2. **Брифы / главная (Briefs)**  
   Эндпоинты вроде `GET /api/v1/briefs/feed`: поле **`image_url`**.  
   Фронт для брифов грузит картинку через **свой** прокси `/api/image-proxy?url=...` и при ошибке пробует прямой URL. Если upstream отдаёт не картинку или блокирует — снова плейсхолдер.

**Требование:** не ломать существующие клиенты. Новые поля (`image_source`, `image_provenance`) — только **опционально**.

---

### Корневая диагностика (что нужно исправить на backend)

1. **RSS без превью**  
   У части источников (About Islam, MuslimMatters, Islam21c, SeekersGuidance и т.д.) в item **нет** нормального изображения. Тогда сейчас часто подставляется **один и тот же Pexels** → визуально «нет фото».

2. **URL есть, но это не картинка или мёртвая ссылка**  
   Нужна **валидация** после выбора URL (см. ниже).

3. **Недостаточное извлечение из RSS**  
   Фронтовый fallback-парсер (если API недоступен) смотрит: `media:content`, `enclosure` (jpg/png/webp), `<img>` в HTML описания, `og:image` внутри контента item.  
   На backend нужно **не хуже и шире**: например `media:thumbnail`, `itunes:image`, специфичные namespace, при необходимости — несколько `media:content`.

4. **Отсутствует шаг «страница статьи»**  
   Если в RSS картинки нет, **обязателен** запасной путь: HTTP GET HTML страницы **`link` статьи** (не главной сайта), разбор:
   - `<meta property="og:image" content="...">`
   - `<meta name="twitter:image" content="...">` / `twitter:image:src`  
   Привести к **абсолютному URL** (`urljoin` с `article_url`).

---

### Алгоритм выбора изображения (строгий приоритет)

Для каждой статьи после парсинга RSS:

1. **Кандидаты из RSS** (все подходящие URL, не только первый попавшийся):
   - `media:content` @url (учитывать type image/\* если есть)
   - `media:thumbnail`, `enclosure` с image/\* или расширения jpg/jpeg/png/webp/avif
   - `itunes:image` (href)
   - все `<img src>` из `content:encoded` / `description` — предпочитать **большую** площадь (width×height из атрибутов), штрафовать `thumb`, `avatar`, `icon`, `logo`, маленькие размеры в пути
   - meta og:image **внутри** CDATA/HTML описания item (если есть)

2. **Фильтр «мусорных» URL** (как на фронте, желательно совпадение логики):  
   Отбрасывать URL, если матчится хотя бы одно:
   - WordPress emoji CDN `s.w.org/images/core/emoji`
   - `gravatar.com`
   - пути с `/emoji/`, `/avatar/`, `/icon/`, `/logo/`, `/logos/`
   - известный мусорный плагин-путь `plugins/islamic-graphics` (или аналоги по вашей статистике)

3. **Если после п.1–2 нет валидного кандидата — скрейп HTML страницы статьи** (`link` из RSS):
   - User-Agent: идентифицируемый бот, например `Mozilla/5.0 (compatible; AllHalalBot/1.0; +https://allhalal.info)`
   - Таймаут **5–8 с**
   - Извлечь og:image, затем twitter:image
   - Снова применить фильтр из п.2

4. **Валидация финального URL** (обязательно хотя бы один из вариантов):
   - **HEAD** или лёгкий **GET** с лимитом тела (например первые 16–32 KB) + проверка `Content-Type` начинается с `image/`, **или** sniff magic bytes (JPEG/PNG/WebP/GIF)
   - Если приходит `text/html` / редирект на логин / **403** — кандидат **отвергнуть**, пробовать следующий кандидат из RSS, затем снова og/twitter, затем п.5

5. **Последний fallback** (только если всё выше не дало валидной картинки):
   - Не использовать **один** фиксированный Pexels URL на весь каталог.
   - Разнообразие: разные запросы/страницы API, выбор **не всегда первого** результата (например детерминированный выбор по `hash(article_id)` из топ-N результатов), ключевые слова из **заголовка** + категория.

---

### Кэш и производительность (критично для продакшена)

- **Не** делать синхронный скрейп **каждой** статьи на **каждый** запрос ленты.  
- Кэшировать по ключу **`canonical article URL`** (или стабильный `guid`):
  - результат: финальный `image_url` / `imageUrl`, HTTP статус валидации, timestamp
  - TTL **12–24 часа** для og/twitter; при ошибке — короткий негативный кэш (например 1–2 ч), чтобы не долбить сайты.
- Фоновые задачи (очередь): при ingest RSS сразу класть задачу «enrich image», а в API отдавать последнее известное значение из БД/кэша.

---

### Логирование и наблюдаемость

Логируйте (без спама в info на каждый item в проде — sampling или debug level):

- `source_id`, `article_url`, итог: `image_source` = `rss` | `og` | `twitter` | `fallback`
- при отбрасывании: причина (`filtered_pattern`, `invalid_content_type`, `http_403`, `timeout`)

Метрика успеха: доля статей с `image_source` in (`rss`,`og`,`twitter`) и успешной валидацией.

---

### Критерии приёмки (explicit)

1. Выборка **30** записей с `/api/v1/news/cached` и **30** с `/api/v1/briefs/feed` (или ваши актуальные эндпоинты):  
   - **≥ 70%** записей имеют непустое поле картинки **и** при `GET` этого URL с сервера возвращается **image/\*** (или sniff OK).  
2. Среди записей с fallback (Pexels/сток): **уникальных** URL ≥ **80%** от числа таких записей в выборке (нет «одна мечеть на 20 статей»).  
3. Для источников без картинок в RSS (список выше): **≥ 60–70%** статей получают уникальное превью через **og/twitter**, а не generic stock.  
4. Не ломать поля, которые уже потребляет фронт (`imageUrl` для news, `image_url` для briefs).

### Проверки после деплоя (команды)

Подставьте реальный базовый URL API.

```bash
# News: сколько записей без картинки
curl -sS "https://API_HOST/api/v1/news/cached?safe_only=false&limit=30" \
  | jq '[.items[] | select(.imageUrl == null or .imageUrl == "")] | length'

# News: уникальность imageUrl
curl -sS "https://API_HOST/api/v1/news/cached?safe_only=false&limit=30" \
  | jq '[.items[].imageUrl] | unique | length as $u | {total: 30, unique_images: $u}'

# Briefs: доля Pexels (если используете)
curl -sS "https://API_HOST/api/v1/briefs/feed?limit=30" \
  | jq '[.items[] | select(.image_url != null and (.image_url | test("pexels")))] | length'

# Ручная проверка одного URL (с вашего сервера)
curl -sSI "PASTE_IMAGE_URL_HERE" | head -n 5
```

### Контекст фронтенда (для согласования, не обязательно менять фронт)

- В репозитории Next.js fallback-парсер RSS дублирует часть логики (`lib/newsFeed.ts`, функция `extractImageFromItem` + `BAD_IMAGE_URL_PATTERNS`). Идеально, чтобы **источник истины** был backend, а ответ API всегда содержал уже очищенный и проверенный URL.  
- Страница `/en/news` часть превью ренерит через **прямой** `<img src={imageUrl}>` — если URL битой или блокируется CDN только для браузера, может понадобиться отдельная задача на фронт (прокси); **но первая линия защиты** — отдавать **корректный и по возможности «разрешённый» URL** и не отдавать HTML-страницы вместо картинки.

### Итог одной строкой

Реализуй **полную цепочку**: RSS (все релевантные поля) → фильтр мусора → валидация → при отсутствии — **og/twitter со страницы статьи с кэшем** → разнообразный stock fallback → метрики и проверки выше.
