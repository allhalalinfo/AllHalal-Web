# AllHalal-Backend: Home (оригинал) vs News (RSS + фильтры)

Документ для репозитория **AllHalal-Backend**. Цель — разделить источники данных и убрать «мусор» из ленты.

---

## 1. Продуктовая логика

| Поверхность | Источник | Содержание |
|-------------|----------|------------|
| **Home** (`GET /api/v1/briefs/home`) | Отдельное хранилище **оригинального контента** | Только статьи, созданные вручную и/или через внутренний AI-пайплайн (редакция allhalal). Никакого автоподтягивания сырого RSS в Home. |
| **News** (`GET /api/v1/briefs/feed` и страница `/news` на фронте) | **Агрегация RSS** | Автоматический сбор, но с **жёсткой фильтрацией**: отсекаем спорт, политику, «общие мировые» новости без связи с уммой / исламским контекстом / halal-тематикой (правила ниже). |

Фронт уже вызывает `…/briefs/home` и `…/briefs/feed`; меняется **только поведение и данные на бэкенде** (плюс при необходимости новые поля в JSON).

---

## 2. Модель данных (рекомендация)

Ввести явный признак происхождения записи:

- `content_origin`: enum  
  - `editorial` — оригинал (ручной + ваш AI), участвует в **Home**  
  - `rss` — импорт из RSS, **только** в **News/feed** (и в выдачах, явно помеченных как RSS)

Альтернатива: две сущности/таблицы (`editorial_posts`, `rss_items`) с маппингом в общий DTO `Brief` для API — но тогда единый сериализатор должен заполнять одни и те же поля (`title`, `dek`, `image_url`, `category`, `published_at`, …).

**Home** должен запрашивать **только** `content_origin = editorial` (или только таблицу оригинала).

**Feed** может отдавать **только** `rss`, или смешанную ленту, если позже решите показывать и оригинал в News — по умолчанию для задачи «News = RSS» достаточно **только RSS** в `/feed`.

---

## 3. Эндпоинты

### `GET /api/v1/briefs/home`

- Источник: БД оригинальных статей (статусы `published`, сортировка по дате / ручной `pinned` / `hero_rank`).
- Формат ответа: как сейчас (`hero`, `featured`, `compact`) — без обязательных изменений на фронте.
- **Запрещено** подмешивать в ответ статьи, у которых `content_origin = rss`.

### `GET /api/v1/briefs/feed`

- Источник: нормализованные RSS-элементы после парсинга и **после** фильтрации.
- Параметры `limit`, `offset`, опционально `category` — как сейчас.
- При пустой выдаче после фильтров лучше отдавать `items: []` и метаданные пагинации, а не «сырые» отфильтрованные мусором записи.

---

## 4. Жёсткая фильтрация RSS (News)

Рекомендуется **многослойный** пайплайн (все слои дешевле LLM — применять по порядку).

### 4.1. Чёрный список по ключевым словам (title + description/summary)

Нормализация: lower case, удаление диакритики опционально. Примеры категорий блокировок (расширяемый конфиг):

- **Спорт:** `premier league`, `champions league`, `fifa`, `nba`, `nfl`, `olympics`, `world cup`, `tennis`, `cricket score`, …
- **Политика / выборы:** `election`, `parliament`, `senate`, `white house`, `kremlin`, `sanctions` (осторожно: часть может пересекаться с уммой — см. allowlist ниже), …
- **Табloid / мусор:** `celebrity`, `gossip`, `dating`, `horoscope`, …

При совпадении — **drop** или карантин `rejected_reason`.

### 4.2. Белый список тематик (мягкий режим)

Если статья не попала под blacklist, но нужно поднять качество: бонус за совпадение с темами вроде:

`islam`, `muslim`, `ummah`, `mosque`, `ramadan`, `hajj`, `umrah`, `quran`, `hadith`, `fiqh`, `halal`, `zakat`, `charity`, `palestine`, `gaza`, `rohingya`, `uyghur`, `refugee` (настраивается).

Вариант политики: **«строгий»** — пропускать только если есть хотя бы один сильный сигнал из allowlist **или** источник из доверенного списка (п. 4.4).

### 4.3. Категории RSS-источника

У каждого фида — поле `default_category` и флаг `trusted_islamic: bool`. Для ненадёжных фидов применять более агрессивный blacklist + optional allowlist.

### 4.4. Список источников

- Разделить фиды на **tier A** (исламские/умма-фокус) и **tier B** (общие новости).
- Для **tier B** обязательны blacklist + (рекомендуется) allowlist или отдельная модель скоринга.

### 4.5. Опционально: лёгкий классификатор / LLM

Только для пограничных статей: бинарная метка `relevant_to_portal: yes/no` с коротким промптом. Не заменять правила 4.1–4.4 — дополнять.

### 4.6. Логирование

Сохранять для отладки: `feed_id`, `url`, `rejected` (bool), `rejected_reason` (`keyword:sport`, `keyword:politics`, `no_allowlist_match`, …). Это упростит подгонку списков без релиза фронта.

---

## 5. Миграция

1. Пометить существующие записи: что было ручным/AI → `editorial`, что из RSS → `rss` (по `source` / `external_id` / отсутствию `rss_guid`).
2. Включить новую логику `/home` только из `editorial`.
3. Включить фильтры на ingest RSS + (по возможности) ретро-очистку уже сохранённых `rss` записей в БД.

---

## 6. Связь с фронтом (Allhalal-Web)

- `lib/briefs.ts` — `getHomepageBriefLayout()` → `…/briefs/home`, `getFeedBriefs()` → `…/briefs/feed`.
- После стабилизации API при необходимости можно добавить в тип `Brief` поле `content_origin` для бейджей («Оригинал» / «Партнёрский материал») — **не обязательно** для первого этапа.

---

## 7. Критерии готовности

- [ ] `/home` никогда не возвращает RSS-only записи.
- [ ] `/feed` не отдаёт очевидный спорт/полит-шум по вашим правилам (проверка на фиксированном наборе статей-тестов).
- [ ] Документация OpenAPI / README бэкенда обновлена.
- [ ] Метрики: доля отфильтрованных статей по дням, топ `rejected_reason`.
